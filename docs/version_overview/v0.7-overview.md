# v0.7 Overview — dev-ready

Target release: v0.7.0 | Status: Release candidate; public release pending
Scope: FR-23, FR-28, FR-24, FR-29; permanent FR-22 N-1 → N gate

## What v0.7 shipped

dev-ready v0.7 completes the methodology layer around generated FastAPI
projects, makes long-running initialization observable, and proves the real
v0.6 → v0.7 overlay-upgrade path. It adds no runtime dependency.

### Configurable Handoff Protocol (FR-23)

- Projects generated with `agents` receive
  `docs/handoffs/protocol.yaml`, the sole runtime Protocol Configuration.
- Seven stable role ids carry editable titles, nullable model assignments,
  responsibilities, prohibitions, handoff order, escalation, reporting, and
  commit authority. Generated prose does not duplicate editable titles or
  model values.
- Fresh projects use process-v2 artifacts: durable specs, tracer-bullet
  tickets, one-ticket execution, Senior review, and separate QA, Security, and
  SRE gates. Active numeric phase directories are ignored; the protocol,
  reusable scaffold, and specs remain durable.

### Complete Spec Loop and 10/10 catalog (FR-28)

- `spec-loop` is one explicit catalog item containing the pinned dependency
  closure for grilling, durable specs, ticket dispatch, domain modeling, and
  architecture improvement.
- Selecting it deterministically resolves the existing `tdd`,
  `diagnosing-bugs`, and `code-review` items. The resolved selection drives the
  confirmation, generated files, report, verification, stamp, check, and
  upgrade. Explicit `none` remains empty.
- The skills catalog is exactly 10/10. Standalone Spec Loop guidance stays
  role-neutral; selecting both Spec Loop and agents adds the four-layer role
  mapping. No rendered guidance points at deselected assets.
- The bundle includes local tracker/domain configuration and does not generate
  a root `CONTEXT.md`. The existing `docs/architecture.md` template remains
  the durable architecture record.

### Installable `dev-ready init` skill (FR-24)

- The original Agent Skill at `skills/dev-ready/SKILL.md` teaches agents to
  build safe, non-interactive `uvx dev-ready init` commands, validate catalog
  ids, handle conflicts and nonzero exits, and verify successful output.
- It is a repository distribution asset, not a generated-project catalog item
  or stamp entry. The canonical install command is:

  ```bash
  npx skills add MoofonLi/dev-ready --skill dev-ready
  ```

### Truthful staged progress and atomic finalize (FR-29)

- `init` reports fetch → overlay → verify → finalize on stderr. TTYs receive a
  standard-library spinner; redirected output receives stable plain lines with
  no animation controls. Stdout retains the final report.
- Typed callback events make progress optional and observational; renderer
  cleanup covers normal completion, failures, exceptions, interrupts, and
  Python-handled termination.
- Staging is adjacent to the destination and finalize uses one same-filesystem
  atomic rename after revalidation. Failure exposes no partial target and an
  initially empty target is restored.

## Upgrade compatibility and lifecycle evidence

The permanent network-tier gate generates with the exact released
`dev-ready==0.6.0` artifact and runs the checkout's `check`, `upgrade
--dry-run`, real `upgrade`, post-upgrade `check`, and repeat `upgrade`.

- Dry run is byte-for-byte non-mutating.
- Upstream application content is preserved.
- The stamp's upstream repository and commit remain immutable Base Provenance.
- The dev-ready version, selected-item pins, and managed inventory advance as
  Overlay Currency. A newer base pin is advisory, not false provenance.
- Untouched obsolete managed files are removed transactionally; modified ones
  are preserved and reported. Repeating the upgrade is a no-op.
- A v0.6 stamp keeps its recorded selection and never acquires the new
  `spec-loop` default or its requirements implicitly.

The N-1 constant remains `0.6.0` for the v0.7 release. It advances to `0.7.0`
only when v0.8 development begins, after the artifact exists publicly.

### Branch B — increasing adjusted PyPI downloads

Qualifies when adjusted downloads are strictly increasing across four
consecutive complete UTC weeks. A complete week is the half-open interval from
Monday 00:00 UTC through the following Monday 00:00 UTC, and all four weeks
must have ended before evaluation.

For each week, record the raw PyPI total, known maintainer-originated download
events, known CI-originated download events, any additional bounded automation
allowance, the evidence used to bound those values, and the adjusted total:

`adjusted = max(0, raw - maintainer - CI - additional bounded automation)`

Subtraction is conservative: use the largest supportable count for maintainer,
CI, and other known automation, not the most favorable estimate. The branch
passes only if `W1 < W2 < W3 < W4`. If CI or maintainer noise cannot be bounded
honestly for any week, branch B cannot satisfy the gate.
