# v0.10 Overview — dev-ready

Release: v0.10.0, patched by v0.10.1 | Status: Released
Scope: FR-32 Mount Points; FR-33 Agent Target Map; FR-34 interview-driven
generation skill; FR-36 selection reach and overlay-infrastructure corrections;
FR-37 tech stack and standards source in the generated `AGENTS.md`; FR-38 secret
hygiene and credential disclosure; permanent FR-22 N-1 → N gate

## What v0.10 ships

v0.10 is the assembly-and-reach version. Nothing here changes how a project is
selected — Category remains the only user-facing axis, and the stamp stays at
version 5 — but the guidance a selection produces now lands where the agent
already reads, far more agents can find that guidance, a generated project can
state its own tooling and standards, and it no longer helps the user commit its
own secrets. There is no new runtime dependency and no change to the base
template's role.

### Mount Points (FR-32, [ADR-018](../decisions/adr-018-spec-loop-spine-and-default-set.md) as amended 2026-08-03)

- Selecting an Enhancement now changes the development-loop skill that acts on
  it. Six of the catalog's Enhancements declare a mount: the security audit and
  the React quality check land inside `code-review`, the web-app testing
  Enhancement lands inside `tdd`, and the two design references and the
  frontend-design Enhancement land inside `implement`. The rest declare none
  and behave exactly as before.
- Guidance arrives as one delimited block appended to the mounted skill, holding
  a single `## Mounted enhancements` section with one entry per selected item,
  sorted by item id. Two Enhancements mounted on the same skill produce one
  block with both entries rather than two blocks.
- Sorting by id rather than by manifest order is deliberate: manifest array
  order reaches no other file's content, and adopting it here would make a
  cosmetic reorder rewrite every project's skill on the next `upgrade`.
- Selecting nothing that mounts leaves each loop skill byte-identical to its
  vendored snapshot, so a lean project pays nothing for the mechanism.
- Injection happens inside the overlay's whole-file rendering, never as a
  catalog effect. The stamp inventory hashes the injected bytes, so a mounted
  skill is a normal managed file: `upgrade` replaces an untouched one and
  preserves and reports an edited one. dev-ready never reads a generated skill
  back and never rewrites one at runtime.
- `THIRD_PARTY_NOTICES.md` now states the licensing fact rather than a
  mechanism: copies written into a generated project may be modified and are
  therefore derived works, while the repository's own vendored snapshots stay
  byte-checked against the pinned commit.

### Agent Target Map (FR-33, [ADR-019](../decisions/adr-019-agent-target-map-drift-guard.md) as amended 2026-08-03)

- dev-ready declares **57 Agent Targets**, up from two in v0.8 and v0.9. They
  are derived by a maintainer script from `vercel-labs/skills` at a pinned
  commit, added to the manifest `vendored` section for provenance, and held to
  the source by the `agent-target-drift` CI job. The property CI enforces is
  that the manifest declares a target for every agent the pinned source gives a
  project-level skills directory other than `.agents/skills`.
- A second derived list records the **19 standard-compliant agents** that need
  no target at all, because they already read Canonical Content at
  `.agents/skills/`. They are excluded by construction rather than by policy —
  a Pointer Stub for one of them would collide with Canonical Content's own
  path — and they are named in the selection prompt and in the generation
  report, so their absence from the target list is never read as a lack of
  support.
- These two numbers are stated here and only here. A count in a README is
  enforced by nothing and rots at the next monthly pin bump; the guarded
  property does not.
- Where two agents share a skills directory, one stub tree is written rather
  than two colliding ones, and the collision guard that catches genuine
  mistakes is untouched.
- Only `skills_dir` is derived. `rules_file` and `mcp_file` have no upstream
  source and stay hand-declared, populated for Claude Code alone. Global skill
  directories in the source point outside the project and are parsed and
  discarded — dev-ready still writes nothing outside the target directory.
- Per-target descriptions are gone: most upstream display names were the
  identifier re-spelled, so the prompt and the report now compose their lines
  from the identifier and the paths actually written.
- **The `--agents` default changed, and it is a user-facing contract change.**
  An absent `--agents` used to resolve to every declared target; at 57 targets
  that would write roughly 684 Pointer Stub files instead of 24. It now
  resolves to `claude`, as does `--yes`. `--agents all` keeps its meaning, which
  is how a user asks for the whole set. The prompt is one flat searchable list
  with `claude` pre-selected on both the Default Set and the custom branch, so
  `--yes` and a plain-Enter interactive run still produce the same project.

### Interview-driven generation skill (FR-34, [ADR-019](../decisions/adr-019-agent-target-map-drift-guard.md) as amended 2026-08-04)

- `skills/dev-ready/SKILL.md` no longer teaches an agent to translate flags. It
  runs a capped interview — one opening question about what the user is
  building, at most three follow-ups for what that answer left ambiguous — and
  then proposes a single command with a reason for each selection, held for the
  user's approval.
- The command it composes is always non-interactive: the interview replaces the
  CLI's prompts rather than chaining into them. With no human in the loop it
  generates the Default Set and reports what it assumed.
- The skill is a third disclosure surface for the standard-compliant agents, and
  the earliest of them, because it runs before the CLI does.
- Its contract test still cross-checks every documented identifier and every
  worked example against the live catalog and the real argument parser, so a new
  catalog item fails the build until the interview knows when to select it.
- Distribution is unchanged: this repository, outside the generated overlay and
  outside the manifest catalog, with no Claude plugin metadata.

### Selection reach and overlay infrastructure (FR-36, the two 2026-08-02 [ADR-018](../decisions/adr-018-spec-loop-spine-and-default-set.md) amendments)

- The `Add Enhancements to the Default Set?` confirmation is gone. Accepting the
  Default Set now leads straight into Category and item selection, which is
  where a user who wanted an Enhancement was already trying to get. Category and
  item menus start with nothing pre-selected, so pressing Enter through them
  still yields exactly the Default Set.
- `docs/architecture.md` and `docs/requirements.md` are unconditional Overlay
  Infrastructure. A project that selects no Category still receives both
  skeletons and a rules file that points at the architecture document. The
  `docs` Component keeps only the two visual design references as selectable
  items.
- The generated development-loop guidance names its Execution step. v0.9
  vendored `implement` and never mentioned it in the one file every agent
  session loads.
- The `setup-all` Catalog Item is retired. Its skill is now part of the
  always-generated development loop, so every project gets it and nobody selects
  it. The identifier exits 2 with the existing retired-identifier message, and a
  stamp that records it migrates rather than being refused.
- The generation-time rewrite that used to strip references to the unselected
  setup skill was deleted with the identifier. Keyed on an id that no longer
  exists, it would otherwise have fired on every generation and removed accurate
  references to a skill that is now always present.

### The generated `AGENTS.md` is a Standards Source (FR-37, [ADR-023](../decisions/adr-023-upstream-facts-drift-guard.md))

- Every generated project — including one that selects nothing at all — now
  names the tools an agent needs in order to implement and verify a change:
  pytest with its coverage floor, `ruff`, both type checkers, Bun as the package
  manager, Biome, `tsc`, and Playwright as the frontend's only test runner. The
  backend-test entry says plainly that the tests need live services and names
  the two scripts that start them.
- `## Stack` names the UI layer as well — Tailwind CSS, shadcn/ui, and the
  TanStack libraries — because an agent that does not know which framework the
  project uses writes the wrong framework's code.
- The file states that it is the project's Standards Source, which is what makes
  the vendored `code-review` skill's Standards axis resolve to something. Naming
  tools alone would not have: that axis is told to skip anything tooling already
  enforces. So the file also carries rules no tool enforces — the generated API
  client and route tree are regenerated rather than hand-edited, a model change
  requires an Alembic migration, and the backend tests mirror the application
  package's layout.
- No version numbers appear in any of it. Tool identity only; `.python-version`
  already owns the Python version.
- Three shipped defects in `## Commands` are corrected: a package manager the
  project does not use, a backend test command that fails without a running
  database and said nothing about it, and a lint command that rewrote files
  instead of checking them.
- The claims are drift-guarded. A stdlib script runs as one step inside the
  existing `generate-and-verify` job and fails when a tool or script the
  generated `AGENTS.md` names is absent from the project built against the pin,
  so the weekly upstream-bump PR passes through the check automatically.

### Secret hygiene and credential disclosure (FR-38, [ADR-022](../decisions/adr-022-upstream-config-not-application-source.md))

Four defects found by generating a project with the released v0.9.0 and reading
what it produced. All four are shipped-product defects rather than new
capability.

- **A generated project ignores its own secrets.** dev-ready writes a random
  `SECRET_KEY`, `POSTGRES_PASSWORD`, and `FIRST_SUPERUSER_PASSWORD` into `.env`,
  and none of the three generated `.gitignore` files carried an `.env` pattern —
  so a user's first `git add .` committed their own secrets. The root
  `.gitignore` is now pruned and replaced by an overlay-managed file carrying
  upstream's entries plus `.env` and `.env*`, the same prune-and-replace shape
  `README.md` already used. Because dev-ready now owns that file, a maintainer
  check reads upstream's root ignore file at the pinned commit itself and fails
  the weekly bump when it diverges from the adopted copy.
- **The generated login is disclosed.** Both the generation report's next steps
  and the generated `README.md` now name the superuser login and say where its
  password is, together with the ordering fact that makes it urgent: the
  generated backend creates that user only when it is absent, so changing
  `FIRST_SUPERUSER_PASSWORD` after the first start changes the file and not the
  login, with no error raised.
- **`BACKEND_CORS_ORIGINS` no longer ships a third party's hostname.** Upstream's
  own local-testing domain is removed from the generated value by a post-Copier
  rewrite of configuration; nothing under `backend/app/` or `frontend/src/` is
  touched.
- **The deployment workflows are no longer pruned.** `deploy-production.yml` and
  `deploy-staging.yml` were written by upstream for downstream users, carry
  upstream's own `github.repository_owner != 'fastapi'` guard, and are exactly
  what the retained `deployment.md` teaches. Pruning them removed a working
  deployment path and left the documentation describing files that were not
  there.

## v0.10.1 — interactive `init` could not get past its own prompts

v0.10.0 shipped an `init` that no interactive user could complete. Two crashes
sat on the default path, one behind the other, and the release gates did not see
either.

- **The multi-select never opened.** FR-33's searchable prompt enabled
  questionary's type-to-filter without disabling the j/k movement keys, which
  questionary refuses to combine — so the first checkbox raised
  `ValueError: Cannot use j/k keys with prefix filter search` on every
  interactive run. Arrow keys still move; j and k now type into the filter,
  which is what the filter was added for.
- **The item prompt was asked with nothing to offer.** Accepting the Default Set
  and adding no Category leaves only `dev`, whose sole item is the development
  loop, so the item prompt received an empty choice list and questionary raised
  `AttributeError: 'InquirerControl' object has no attribute 'pointed_at'`. The
  prompt is now omitted when the chosen Categories offer nothing outside the
  development loop, and `docs/cli-spec.md` step 5 records that it is
  conditional. This crash was only reachable once the first was fixed.

Nothing about the selection model, the flags, the exit codes, the stamp, or the
generated files changed. A default interactive run still produces exactly
`ProjectSelection.default_set` with the `claude` Agent Target.

**Why the v0.10.0 gates missed it.** The only test covering the questionary
adapter monkeypatched questionary away and asserted the argument dev-ready
passed, which cannot disagree with the code; every other prompt test injected a
`FakeAsker`, and the sole e2e `init` test uses `--yes`, a path that by design
never imports questionary. The line where dev-ready's arguments crossed into a
third-party library had no coverage at all, and the gap was structural rather
than an omitted case. `tests/README.md` now requires that an adapter to a
third-party library be driven through the real library at least once, and
`tests/unit/test_prompts.py` drives `QuestionaryAsker` and one whole
`collect_answers` flow over `create_pipe_input()`/`DummyOutput()` — headless, no
console needed. Both crashes fail those tests.

**Deviations.** This patch ran `implement` alone: `grill-with-docs`, `to-spec`,
and `to-tickets` were skipped with Moofon's authorization, on the grounds that
the work fit one session, one footprint, and settled nothing that outlives it.
That is a deviation from the four-step loop AGENTS.md states without an escape
hatch — recorded here rather than normalized. Whether the loop should carry a
documented escape hatch, in this repo and in the skills dev-ready generates, is
open for v0.11 and needs a decision record, not precedent. Two smaller items rode
along: the new `tests/README.md` rule is a repo-wide testing standard introduced
without an ADR, and `prompt-toolkit` was declared as a dev-only dependency
(noted in `docs/architecture.md`) because questionary's own `>=2.0,<4.0` range is
too loose for an API the tests call directly.

## Upgrade from v0.9 ([ADR-014](../decisions/adr-014-truthful-overlay-lifecycle-state.md))

The stamp stays at version 5, so `dev-ready upgrade` re-applies the v0.10 overlay
without a migration and without asking the user to choose again. Base Provenance
stays immutable; only Overlay Currency advances. A dry run reports the whole
write-and-delete plan without changing a byte, a failure rolls writes and
deletions back together, and a repeat successful upgrade plans no further change.

**The secret-hygiene fix does not reach an existing project, and this is the one
thing to know before upgrading.**

- An untouched `README.md` **is** replaced, because it has been an
  overlay-managed file since v0.2. FR-38's credential disclosure therefore does
  arrive in an upgraded project.
- `.gitignore` **is not**. A v0.9 project carries upstream's own copy at that
  path — a file dev-ready never wrote and has no record of — and ADR-014 forbids
  replacing it. `upgrade` reports it under `Skipped (user-modified)` and moves
  on.
- **The manual action:** add `.env` and `.env*` to the project's root
  `.gitignore` by hand. Adding the pattern does not remove an `.env` already
  committed to history; a secret that has been pushed is rotated, not ignored.
- That skip is ADR-014 working, not failing. The alternative — dev-ready
  overwriting a file it never wrote because it happens to know a better version
  — is the behaviour the rule exists to prevent, and a special case for this one
  path would have bought the fix at the cost of the guarantee.

A project that recorded the retired `setup-all` identifier upgrades without
manual editing, and a project that never selected that Enhancement receives the
skill anyway as part of the always-generated loop. A mounted skill the user
edited survives untouched and is reported as divergent. The permanent
network-tier gate exercises the whole path from the released `dev-ready==0.9.0`
artifact and finishes with a clean `check`.

## Deviations from the accepted specs

Recorded so the next reader does not have to reconstruct them from the log.

- **An architecture refactor rode the version that no spec asked for.** Three
  restated rules were collapsed into deep modules immediately after the v0.9.0
  tag, which is where `src/dev_ready/agent_targets.py` came from. It was
  hygiene ahead of FR-33 rather than FR-33's own work, and it is recorded here
  because it is not derivable from any of the six specs.
- **The dependency floor moved.** `questionary` is now required at 2.1 or later,
  for the searchable single-list prompt FR-33's 57 targets need. No dependency
  was added, and the "no new runtime dependencies in v0.10" constraint holds,
  but a minimum-version bump is a change a reader of the specs would not expect.
- **One assertion was repaired outside every ticket footprint.** Phase 3 landed
  the `--agents` default change but left the network-marked
  `tests/e2e/test_init_real.py` asserting that a `--yes` run writes a second
  target's directory — a contract FR-33 had just removed. The gate was red on
  `main` before Phase 5b began and no Phase 5b change caused it. The assertion
  was inverted to FR-33's actual contract rather than deleted, so the coverage
  survived with the failure.
- **FR-37 left one command out on purpose.** The spec declined to write
  `uv run prek run --all-files` into the generated `AGENTS.md`: upstream's
  pre-commit configuration survives pruning but references a script dev-ready
  prunes, and "it should never fire" is not enough to ship a command into every
  generated project.
- Nothing else in the six specs was asked for and not delivered.

### Branch B — not re-derived

repository's own design: the permanent `upgrade-from-release` CI job installs

been done. The v0.7 rider's own failure condition applies, and v1.0's gate is

## Deferred scope

- v0.11: `setup-project` at the head of the generated development loop (FR-39),
  the full `awesome-design-md` set as Design References (FR-40), and MIT notice
  propagation into generated projects (FR-41).
- FR-41 is the one v0.10 created the standing for. The twelve MIT
  `mattpocock/skills` development-loop skills carry no copyright or permission
  notice into generated projects, while the two Apache-2.0 skills carry their
  `LICENSE.txt`. The gap predates v0.10 by three versions, but v0.10 is the
  first version whose own `THIRD_PARTY_NOTICES.md` calls those copies derived
  works and whose generation injects dev-ready's own text into them. Repairing
  it means a new managed path, a stamp-inventory entry, and drift-guard
  coverage — feature work, which a release phase does not carry. It is scheduled
  rather than merely recorded.
- v1.0 after the real-users gate: FR-27, a standalone full-stack Next.js
  template, and reconsideration of the Web UI.
- Not in v0.10: a replacement multi-agent scaffold in any size, a second
  development loop, a measured context budget, a localized runtime, the GitHub
  MCP catalog item, forking or renaming the vendored setup skill, and any change
  to where Canonical Content and Pointer Stubs are written.

Report release or generation problems at
