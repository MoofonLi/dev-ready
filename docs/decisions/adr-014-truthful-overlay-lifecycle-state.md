# ADR-014: Separate immutable Base Provenance from Overlay Currency

- Status: Accepted (2026-07-25)
- Context: `dev-ready upgrade` changes only overlay-managed content, but the v0.6 implementation rewrites the stamp's upstream commit from the running CLI manifest. Once the upstream pin advances, that would claim application content was regenerated when `backend/`, `frontend/`, and every other upstream path were deliberately preserved. Conversely, `check` does not currently treat an older `dev_ready_version` as overlay drift, so it cannot express the distinction honestly. The permanent N-1 to N gate in v0.7 makes this ambiguity a compatibility contract rather than an internal detail.
- Decision: The stamp's upstream repo and commit are **Base Provenance** and remain immutable across overlay-only upgrades. The stamp's dev-ready version, selected catalog-item pins, and managed-file inventory are **Overlay Currency** and advance when an upgrade applies the current overlay. `check` treats stale Overlay Currency as drift, but reports a newer manifest upstream pin as a non-blocking base-update advisory because `upgrade` cannot act on it. A successful overlay upgrade can therefore produce a clean check without falsifying Base Provenance. Upgrade also retires obsolete overlay-managed files only when their current bytes still match the recorded hash; deletion is part of the existing transaction and rollback, while modified obsolete files are preserved and reported.
- Consequences: The N-1 test must assert both byte-preserved upstream content and byte-preserved Base Provenance. JSON and text check reports distinguish drift from advisories. No online or implicit upstream-update path is introduced. Users who want a newer base template still regenerate a project; `upgrade` remains offline and overlay-only.
