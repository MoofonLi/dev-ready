# ADR-022: dev-ready modifies upstream configuration, never upstream application source

- Status: **Accepted** (2026-08-04, Moofon). Targets v0.10 and every version after it; scopes what FR-22 already promised for `upgrade` onto `init` as well.
- Context: a project generated with v0.9.0 ships `frontend/src/components/Common/Footer.tsx` exactly as upstream wrote it — three social links pointing at `github.com/fastapi/fastapi`, `x.com/fastapi` and `linkedin.com/company/fastapi`, above the line `Full Stack FastAPI Template - <year>`. Every dev-ready project therefore publishes a footer that names the template instead of the user's project and links to a third party's accounts. Three repairs were weighed — add dev-ready's own repository link beside the existing three, replace them with it, or strip them and template the caption with the project name. The question does not stop at the footer: the same argument reaches the document title, the favicon, the login page's copy, and the seed data. Until now dev-ready had no stated rule, only the accident that it had never yet edited application code. FR-22 states the rule for `upgrade` ("never touches upstream application code") and nothing states it for `init`.
- Decision: **dev-ready writes and rewrites upstream *configuration*; it never edits upstream *application source*.**
  - Configuration is what dev-ready already touches, and it stays permitted: Copier answers rendered into `.env`, an npm dev dependency and script added to `frontend/package.json`, MCP servers written into `.mcp.json`, and the whole-file prune-and-replace of repository-maintenance and documentation files that FR-7 and FR-8 established for `README.md`. FR-38 adds `.gitignore` to that set by the same prune-and-replace shape.
  - Application source is never edited, patched, templated, or string-substituted. That covers everything under `frontend/src/` and `backend/app/`. `Footer.tsx` keeps upstream's links and upstream's wording.
  - The test for a file dev-ready has not met before is its **role, not its path**: a file a tool or a runtime reads as settings is configuration; a file that is compiled, bundled, imported, or served to an end user is application source. A configuration file living inside `frontend/` is still configuration.
- Considered options:
  - **Adding dev-ready's repository link to the footer** — rejected. It places dev-ready's marketing inside a product that is not dev-ready's, on a surface addressed to the user's own end users. It also defeats itself: the first thing a user does is delete it, and deleting it makes the file user-modified, which under ADR-014 excludes it from `upgrade` permanently. The outcome is a removed advertisement plus a file that diverges forever. The v1.0 real-users gate does need attributable signals, but the generated `README.md` and the generation report address developers, which is where that signal has to come from.
  - **Replacing the FastAPI links with dev-ready's** — rejected for the same reasons, and additionally because it substitutes one party's attribution for another's inside that other party's file.
  - **Stripping the social links and templating the caption with the project name** — the strongest of the three, and still rejected. It repairs two real defects, but it is the first patch to application source and nothing after it has a principle to stop on. A user who wants a different footer edits eight lines of TSX; a user who wants dev-ready to keep its hands off their UI has no way to ask.
- Consequences: every generated project's footer names the upstream template and links to FastAPI's social accounts until its owner edits it, and this will be reported as a defect again — the rejection is recorded here so the next report is answered rather than re-litigated. The same rule forbids seeding the page title, the favicon, and the marketing copy. It does not forbid documenting the situation: naming the footer as something to change is `README.md`'s business, and permitted. When FR-27 adds a second base template the rule transfers unchanged, because it is stated in terms of file role rather than of this template's layout.
