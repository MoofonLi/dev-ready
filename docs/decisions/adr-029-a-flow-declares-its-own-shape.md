# ADR-029: An Engineering Flow declares its own chain and its own mount roles

- Status: **Accepted** (2026-08-20, CEO Moofon). Targets v0.12. Amends [ADR-018](adr-018-spec-loop-spine-and-default-set.md)'s Mount Point decision, which named a skill directly, and supplies the field [ADR-024](adr-024-engineering-flow-selection-spine.md)'s 2026-08-18 amendment needed but did not define. [ADR-026](adr-026-setup-project-is-project-infrastructure.md) is unchanged and load-bearing here.
- Context: v0.11 shipped one Engineering Flow, so every question of the form "which step does this attach to?" could be answered with that flow's own skill name. FR-47 adds a second flow whose twelve skills share no name with the first's. Four facts were measured on 2026-08-20, during the v0.12 Phase 2 `grill-with-docs` session and before any code was written.
  - **The manifest stops loading the moment a second flow exists.** Seventy-eight Catalog Items declare a `mount` — 74 Design References plus `react-doctor`, `security-audit`, `webapp-testing`, and `frontend-design` — and its value is always `code-review`, `tdd`, or `implement`. `manifest/loader.py:167-172` requires every mount to name a step of **every** development loop. `obra/superpowers` ships `test-driven-development`, `requesting-code-review`, `executing-plans`, and `subagent-driven-development`; it ships nothing called `code-review`, `tdd`, or `implement`. The failure is not one red test, it is `ManifestError` from every test that loads the catalog. `overlay/rendering.py:141-144` then raises `OverlayError` for the same reason at generation time, so relaxing the loader alone moves the failure from the maintainer to the user.
  - **The chain is already hardcoded, in the one place no test can read it.** `overlay/rendering.py:31-56` holds `_FLOW_GUIDANCE`, a dict keyed by flow id whose `rules` value is a Python string containing the sentence `setup-project` → `grill-with-docs` → `to-spec` → `to-tickets` → `implement` → `improve-codebase-architecture`. Phase 2 must write a second such string for `superpowers`, and that one contains a fork.
  - **The guard ADR-024 specified cannot be written.** It asks the frontmatter test to assert the declared `invocation` against every step a flow ships. `mattpocock` declares `user` and ships twelve steps, of which six declare `disable-model-invocation: true` and six do not. Measured across all twelve template directories: the six that declare it are exactly the chain entries plus `setup-matt-pocock-skills`; the six that do not are the tools. `steps` holds all twelve and nothing separates them, so the list the test needs does not exist as data.
  - **Superpowers' chain forks and mattpocock's does not.** Upstream's declared order is brainstorming → using-git-worktrees → writing-plans → **subagent-driven-development *or* executing-plans** → test-driven-development → requesting-code-review → finishing-a-development-branch. A chain field that cannot express a choice cannot describe this flow.
- Decision: the flow owns the answers to "what order?" and "which step plays this part?", and both become manifest data.
  - **A development-loop Catalog Item declares `chain`** — the ordered entries of its [[Flow Chain]]. An entry is a step id, or a list of step ids when the flow offers a choice at that position. `chain` entries must be a subset of `steps`; the loader asserts it. **`setup-project` is not a `chain` entry.** It is unconditional non-catalog infrastructure under ADR-026, and rendering prepends it to every flow, so listing it would put one fact in two places and let them disagree.
  - **A development-loop Catalog Item declares `roles`** — a mapping from role name to the set of its own steps that play that part. `mattpocock` maps `build → [implement]`, `test → [tdd]`, `review → [code-review]`. `superpowers` maps `build → [subagent-driven-development, executing-plans]`, `test → [test-driven-development]`, `review → [requesting-code-review]`.
  - **A mounted Enhancement declares a role, never a step.** `mount: "implement"` becomes `mount: "build"`. The value space stops being one flow's vocabulary and becomes a vocabulary both flows implement.
  - **A role resolves to a set, not to one step.** `build` covers both branches of the superpowers fork, so `mounted_enhancements` emits one destination per resolved step and an enhancement reaches the user whichever branch they take. Every other role resolves to a set of one. The duplication is in the repository, not in the user's session: a user takes one branch.
  - **The loader validates in both directions.** Every role a mounted item names is declared by every flow — the same strength `loader.py:167-172` has today, restated in role space. Every role a flow declares resolves to steps that flow actually ships. The second half is new, and it is what turns a typo like `test-driven-developement` into a load-time error instead of an `OverlayError` in a user's terminal.
  - **Every step id must have a `paths` entry whose destination leaf equals it.** ADR-024's amendment asserts this rule already exists; it does not. Verified on 2026-08-20 by appending `this-skill-does-not-exist` to `mattpocock`'s `steps` — the manifest loaded without complaint. `_parse_item_kind_and_steps` (`loader.py:797-843`) checks the list is non-empty, that each entry matches the id pattern, and that no entry repeats; it never reads `paths`. **The rule runs in one direction only.** `mattpocock` declares one path that is not a step, `claude/mattpocock` → `docs/agents`, and `superpowers` will declare twelve whose leaf is `LICENSE`. The rule passes today's data unchanged.
  - **The frontmatter guard is asymmetric, and each half is separately true.** `invocation: user` asserts that every **chain entry** declares `disable-model-invocation: true`. `invocation: model` asserts that **no shipped step** declares it. A symmetric rule fails on `setup-matt-pocock-skills`, which declares the flag and is not a chain entry — `setup-project` reaches it and nothing follows it. Verified: `mattpocock`'s five chain entries all declare the flag, and none of superpowers' twelve does.
  - **The generated chain sentence renders from `chain` and `invocation` together, and describes its head separately.** `setup-project` declares `disable-model-invocation: true` and heads every chain, so a `superpowers` project's chain is a user-invoked head followed by model-invoked entries. A sentence claiming the agent starts every step is false about entry zero, in the flow where it would otherwise be true of everything else.
- Considered options:
  - **A per-flow map on each mounted item** (`mount: {"mattpocock": "implement", "superpowers": "executing-plans"}`) — rejected. It needs no loader change and no new flow field, and it is the cheaper edit today. It fails at the third flow: FR-48 is already scheduled for v0.13, and adding it would mean editing 78 items again. Roles put the per-flow knowledge in the one place that changes when a flow is added.
  - **Mounting into the flow's guidance instead of into a skill file** — rejected. It removes the coupling entirely, but it moves the reminder away from the moment it applies, which is the whole point ADR-018 recorded, and it silently changes what a `mattpocock` project has received since v0.11.
  - **Dropping a mount that the selected flow cannot satisfy** — rejected. A user who selects a Design Reference and never sees it referenced has lost data with no message.
  - **Keeping the guard whole-set and weakening it to "at least one step declares the flag"** — rejected. It needs no `chain` field, and it would not notice upstream removing the flag from `implement`, which is the drift on the `mattpocock` side worth catching.
  - **Deriving the chain by name** rather than declaring it — rejected. It is the same class of mistake as deriving the subagent axis from a directory name: a claim about meaning resting on a string.
- Consequences: `mount` values change on 78 Catalog Items. Seventy-four regenerate from one line in `scripts/sync_design_references.py:78`; four skills are edited by hand. `_FLOW_GUIDANCE` shrinks but does not disappear — the chain sentence renders from data, while each flow's convention paragraph and its `setup-project` contribution stay authored prose keyed by flow id, and `_selected_flow_guidance` still raises `OverlayError` for a flow with no entry. `mounted_enhancements` gains the resolved flow as an input, because a role cannot be resolved without knowing which flow was selected. The Generation Skill stops stating a chain at all: with `chain` as data rendered into `AGENTS.md` and `docs/agents/<flow-id>.md`, a third prose copy in `skills/dev-ready/SKILL.md` is a drift surface with no guard, and it would need editing again at FR-48. v0.12's plan called Phase 2 a data-only addition; this decision is why that is no longer true.
