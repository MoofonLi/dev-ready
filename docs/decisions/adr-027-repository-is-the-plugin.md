# ADR-027: The repository is the plugin — a manifest describes, a catalog publishes, a directory sells

- Status: **Accepted** (2026-08-17, CEO Moofon). Targets v0.11 Phase 4; governs FR-45. ADR-003 (as amended 2026-08-12), ADR-009, ADR-011, ADR-015, ADR-016, ADR-021, and ADR-024 (as amended 2026-08-13) remain binding on it.
- Context: FR-45 states that dev-ready's Generation Skill "lacks a **browsable storefront**", and specifies the fix as two files — `.claude-plugin/plugin.json` and `.codex-plugin/plugin.json` — each pointing at the unchanged `skills/dev-ready/` directory. Measured against both published specifications on 2026-08-17, that fix installs nothing in either ecosystem, because it collapses three distinct artifacts into one word.
  - A **plugin manifest** describes one plugin to one ecosystem. It reaches nobody on its own. Claude Code requires only `name` in it; Codex requires `name`, `version`, and `description`.
  - A **marketplace catalog** publishes plugins so a user can install them by name. Claude Code's `/plugin marketplace add owner/repo` fetches `.claude-plugin/marketplace.json` from the repository root, and Codex's `codex plugin marketplace add owner/repo` fetches `$REPO_ROOT/.agents/plugins/marketplace.json`. Neither command has any other entry point into a repository.
  - A **plugin directory** is the browsable storefront FR-45 actually asks for, and it is reached only by review. Claude's is `anthropics/claude-plugins-community`, entered through a submission form and automated safety screening. Codex's is the universal Plugin Directory shared with ChatGPT, entered through the submission portal after human review.

  Two further facts were measured and change the shape. First, `"source": "./"` is a documented pattern in both ecosystems: the repository root may be both the catalog and the plugin, which is what lets one skill directory serve every channel without a second copy. The Codex form was verified against a shipped repository — `appwrite/codex-plugin` keeps its catalog at `.agents/plugins/marketplace.json` and writes `"path": "./plugins/appwrite"`, so the path resolves against the repository root rather than against the catalog's own directory. Second, a **skills-only plugin qualifies for both public directories**. Codex's submission page states that "A plugin can contain skills, an MCP server, or both", and its MCP requirements — a production server URL, domain verification, tool annotations — are conditional on the plugin containing MCP. An in-session claim that dev-ready was structurally excluded from Codex's directory was wrong and is corrected here.
- Decision: **the repository root is the plugin**, published through two catalogs and submitted to two directories.
  - **Four files, not two.** `.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json`, `.codex-plugin/plugin.json`, and `.agents/plugins/marketplace.json`. Both catalogs declare the repository root as the plugin's source, so `skills/dev-ready/SKILL.md` remains the single copy every channel serves. **Neither manifest may fork the skill**, and the cross-agent installer (`npx skills add MoofonLi/dev-ready --skill dev-ready`) remains the documented primary channel.
  - **`dev-ready` names the plugin and the marketplace in both ecosystems.** One public identifier across the GitHub repository, the PyPI package, the skill, the plugin, and the marketplace. The consequence is accepted rather than worked around: Claude namespaces plugin skills by plugin name, so the skill is invoked as `/dev-ready:dev-ready`. Renaming `skills/dev-ready/` would remove the doubling and break `--skill dev-ready`, which is the documented install argument and is asserted against both READMEs by the Generation Skill's contract test.
  - **Submission is a human step taken after the release tag, and acceptance says "submitted".** Both directories are entered by a form, and Codex additionally requires the submitter's individual identity verification in the OpenAI Platform plus at least five positive and three negative test cases. Claude's catalog pins an approved plugin to a commit SHA and syncs nightly, so submitting before the tag pins pre-release content. No version may be gated on another organization's review queue, so the criterion is that both submissions were made and their outcomes recorded — never that either was listed.
  - **The eight submission test cases are committed**, at `docs/plugin-directory-submission.md`, and are derived from the Generation Skill rather than invented. The commands in the positive cases are parsed by the same contract test that already parses the skill's worked examples; the negative cases describe refusals and have no command to parse, so they stay prose.
  - **Three exposures, three answers.** *Schema drift* — both formats are published by other people and change without notice — is genuinely unguardable and stays a by-hand re-verification at every bump, the standing exposure ADR-015 recorded for agent paths before FR-33 closed it. *Version drift* is guarded: Claude pins an installed plugin to the `version` string and delivers updates only when it changes, and Codex requires the field, so a test asserts each manifest's `version` equals `dev_ready.__version__` and the `release` skill bumps four files rather than two. *Repository-root content* is guarded: because the plugin root is the repository root, a future root-level `agents/`, `commands/`, `hooks/`, `bin/`, `.mcp.json`, `.lsp.json`, `settings.json`, or `monitors/` would ship to every installed user without a word, so an offline test asserts the root holds none of them and that `skills/` holds exactly `dev-ready`.
- Considered options:
  - **Two `plugin.json` files, as FR-45 specifies** — rejected on measurement. Neither ecosystem offers an install command against a repository that has no catalog, so the phase would ship files that produce no install path, and Phase 5's by-hand install verification could not pass.
  - **A subdirectory plugin, sourced by `git-subdir`** — rejected. The only directory holding the skill is `skills/dev-ready/`, so the manifest would land at `skills/dev-ready/.claude-plugin/plugin.json` and ride along into every user's skills directory through the cross-agent installer, which copies the whole skill folder. It also trades the one property FR-45 requires — one skill, one copy — for a smaller cache footprint.
  - **Claude only, dropping the Codex half** — rejected once the skills-only qualification was measured. Codex's catalog costs two small files and reaches the same reviewed directory.
  - **Submitting during Phase 4, before the release** — rejected. It starts the review queues earlier at the cost of pinning a commit whose READMEs do not yet describe the plugin install path.
  - **A CI job running `claude plugin validate .`** — rejected. It needs the `claude` CLI as a global tool, which the standing constraints forbid tests to depend on. It stays a by-hand step alongside the two installs.
- Consequences: The repository root becomes a shipping surface. Anyone adding a top-level directory must now ask whether it is plugin content, and the guard test is what asks on their behalf; when Claude or Codex adds a component type, that test's list is one more thing that must be updated by hand. Installing the plugin copies the tracked repository — measured at 4.8 MB across 366 files on 2026-08-17, against the roughly 15 MB of runtime dependencies `uvx dev-ready` already installs — into `~/.claude/plugins/cache`, once per installed version. The two public names are effectively permanent: Claude registers one marketplace per name per user, and renaming a published plugin requires a `renames` map in the catalog to carry existing installs. The version string now lives in four files, and the `release` skill is the only thing keeping them equal outside the test. Codex's directory submission depends on Moofon's individual verification in the OpenAI Platform, which is outside this repository and has no stated turnaround; the version does not wait on it.
