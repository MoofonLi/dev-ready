# ADR-020: The Handoff Protocol is dev-ready's own process, not a generated artifact

- Status: **Accepted** (2026-07-27, CEO Moofon). Targets v0.9. Retires FR-10 and FR-23 from the generated overlay and scopes ADR-007 to this repository's internal process; ADR-013 is unaffected.
- Context: Since v0.2 every generated project could receive a scaffold for a seven-role, four-layer multi-agent process: a Protocol Configuration declaring role ids, responsibilities, prohibitions and model assignments, plus review-gate templates, a ticket directory, and an execution-report skeleton. v0.7 made that configuration authoritative data (FR-23) and it was the headline work of that version. It is also, in substance, dev-ready's own development process — the one this repository runs — productized on the assumption that other teams would want it. Three things now argue against that assumption. It presumes a *team of agents* rather than one developer working with one agent, which is what an ordinary user of a FastAPI scaffold has. It arrives before it is wanted: a user generating their first project receives seven role definitions and four review gates for work that does not exist yet, and ceremony delivered before the work it governs is ceremony a user deletes. And it competes with the thing that does earn its place — the within-session development loop — for the same attention in the same generated instruction surface. Against this, the only evidence of value is this repository's own use, which is not evidence that a *generated* project needs it: dev-ready develops dev-ready and keeps its process either way.
- Decision: stop generating it.
  - **The Handoff Protocol scaffold is removed from the overlay.** Generated projects receive no Protocol Configuration, no review-gate templates, no ticket directory, and no execution-report skeleton. The selectable unit that produced them is removed with them.
  - **dev-ready's own process is untouched.** ADR-007 remains in force for this repository, scoped to internal process only; ADR-013's four-layer loop, the role definitions in `AGENTS.md`, and `docs/handoff/<version>/` continue exactly as they are. What ends is productization, not practice.
  - **Existing projects are migrated, not stranded.** The generated files retire through ADR-014's obsolete-file machinery in the same transaction as the v0.9 stamp migration: untouched files are deleted, files the user edited are preserved with their deletion skipped, and both outcomes are reported.
  - **The multi-agent capability is not replaced.** No smaller scaffold, no optional preset, no documentation stub stands in for it. A team that wants this process can read how this repository runs it.
- Considered options:
  - **Keeping it, defaulted off** — rejected: it preserves the full maintenance surface (a configuration schema, seven role records, six templates, their rendering, their conditional interaction with the development loop, and their share of every migration) to serve a selection nobody has been observed making. Default-off reduces what users receive without reducing what the project carries.
  - **Keeping it, defaulted on** — rejected: it is the single heaviest item in what a project receives by default, in the version that deliberately makes that set small (ADR-018).
  - **Replacing it with a lighter two-role scaffold** — rejected: this invents a second unvalidated design to fix the first one's lack of validation. If real demand appears, it should shape whatever replaces this rather than being guessed at now.
  - **Deferring the removal to v1.0** — rejected: v0.9 already pays for a stamp migration and an obsolete-file pass for other retired ids, so removing this now costs one more entry in machinery already being built, while deferring it means paying for a second migration later.
- Consequences: Two shipped FRs are retired, one of which was a version's headline work. This is a deliberate scope reduction and it is not cheap to reverse — restoring it later means re-authoring the templates, the configuration schema, and its conditional interaction with the development loop. Documentation across the README pair, the version plan, and the requirements index must stop describing a capability that no longer exists, and the description of what dev-ready produces narrows accordingly. Users who adopted the scaffold lose it on upgrade; their edited files survive, so the loss is recoverable by hand from their own tree. Conditional rendering between the Handoff Protocol and the development loop disappears entirely, which removes a combinatorial case from generation, verification, and every future migration.
