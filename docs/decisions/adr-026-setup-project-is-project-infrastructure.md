# ADR-026: `setup-project` is unconditional project infrastructure, and per-flow text lives in one table

- Status: **Accepted** (2026-08-14, Moofon). Decided in the v0.11 Phase 2 `grill-with-docs` session. Targets v0.11 Phase 2. It corrects FR-39 and the v0.11 plan's Phase 2 bullet, both of which deliver the skill as a path inside the [[Engineering Flow]]'s own `paths` list.

  **Amended 2026-08-15** (Moofon, second Phase 2 `grill-with-docs` pass), on three points. The "written unconditionally" bullet named the wrong precedent, and the precedent it named would have shipped `setup-project` with no [[Pointer Stub]] at any [[Agent Target]]. The template source root was left unstated, and both available locations were wrong. And the Context below counts one flow-dependent part where there are two — the issue-tracker section is the second. Each is corrected in place under Decision; the original Context wording is left standing so the miscount is legible rather than erased.
- Context: FR-39 calls `setup-project` "an always-generated setup step at the head of the development loop", and then delivers it as a path inside the flow's `paths`. With one flow in the catalog those two sentences produce identical output, so the contradiction is invisible today. It becomes visible in v0.12, when `superpowers` ships, and again in v0.13.

  Measured against what the skill actually does, three of its four parts belong to the base template rather than to the flow: the superuser `.env` values, the SMTP and Sentry gate, and the started-project detection. Only the hand-off to `setup-matt-pocock-skills` depends on which flow was selected. A flow-owned file therefore carries one copy of the base-template interview per flow, and a later correction to the superuser procedure has to be made in each of them.

  Separately, three pieces of generated text now vary by flow: the hand-off paragraph inside `setup-project`, the [[Flow Chain]] sentence in the generated `AGENTS.md`, and the human explainer at `docs/agents/<flow-id>.md`. The renderer this replaces hardcodes one flow id (`overlay/rendering.py:22`), which is the shape that stops working the moment a second flow exists.
- Decision:
  - **`setup-project` is written unconditionally.** It is not in any flow's `paths`, it is **not** added to any flow's `steps` — after this decision the flow does not ship it — and it is not a [[Catalog Item]]. It stays out of the manifest `vendored` section, so the FR-16 drift guard is untouched, exactly as FR-39 requires.
  - **It is unconditional the way a skill is, not the way a document is** (amended 2026-08-15). The FR-36(b) documentation scaffold this ADR originally cited as its precedent is consumed at `overlay/__init__.py:107`, **after** the Pointer Stub projection at `:91-105`. That projection builds one stub per [[Agent Target]] by scanning already-collected content for `.agents/skills/<name>/SKILL.md`, so following the document precedent literally writes the [[Canonical Content]] and no stub at all: a generated project would hold `.agents/skills/setup-project/SKILL.md` while `.claude/skills/` holds nothing, leaving the one chain entry the generated `AGENTS.md` names first as the only one an agent cannot discover. Every other chain entry escapes this because the catalog loop at `:72-88` runs before the projection. **`setup-project` therefore joins the content mapping before the Pointer Stub projection**, which needs no new mechanism — the existing loop then mirrors it like any other skill. The constraint is stated as an ordering rule rather than as a stub count because it is mechanism-independent: [ADR-025](adr-025-skill-delivery-mode.md) replaces stubs with `symlink`/`copy` in v0.12 from the same projection step and the same collected set, so a `setup-project` added after it would be missed by all three mechanisms and by v0.12's migration.
  - **Its source lives at `templates/skills/setup-project/`, a new root for dev-ready-original skills** (amended 2026-08-15). `templates/claude/skills/` is where `sync_vendored.py` materializes manifest-declared snapshots (`copytree(..., dirs_exist_ok=True)`), and there is no orphan detection there, so an original skill placed among them would not fail anything — it would simply be indistinguishable from content that must never be hand-edited, which is the opposite of what `setup-project` is. `templates/claude/mattpocock/` is the flow's own original content and is ruled out by this ADR's first bullet. The new root makes the distinction structural: everything under `templates/claude/skills/` is vendored without exception, and every dev-ready-original skill is under `templates/skills/`. v0.12's second flow inherits the answer instead of re-deciding it.
  - **Its flow-dependent paragraph is a template token**, filled from the selected flow id at generation time. The source file is therefore `SKILL.md.tmpl` — `render_asset` expands tokens only for that suffix and `collect` strips it — and the authored text may contain no literal `{{` or `}}`, because `rendering.py:71` raises `OverlayError` on any double brace surviving expansion. That is a real constraint for a document about `.env` configuration, where Compose and Traefik syntax both reach for braces.
  - **Per-flow prose lives in one table in `overlay/rendering.py`**, keyed by flow id, holding the chain guidance and the hand-off paragraph. A selected flow with no entry raises `OverlayError` rather than rendering an empty section.
  - **The whole issue-tracker section is per-flow, and the table entry carries it** (amended 2026-08-15). This ADR's Context counted one flow-dependent part; there are two. `docs/agents/issue-tracker.md`, `domain.md`, and `triage-labels.md` all arrive on `mattpocock`'s `claude/mattpocock` → `docs/agents` path, and `setup-matt-pocock-skills` is one of its `steps`, so a *shared* section reading that file and offering that delegation would, from v0.12, read a file `superpowers` never wrote and offer a skill it never installed. The state read moves into the table entry alongside the delegation; the shared interview covers superuser, email, and Sentry — the three that are genuinely base-template facts. The section menu is consequently three shared entries plus whatever the flow contributes, rather than a fixed list. An existence check in the shared section was rejected: it keeps flow knowledge in shared code behind a conditional, and each new flow re-opens the question at a higher cost than the table already pays.
  - **The human explainer needs no new mechanism.** It rides the flow's existing dev-ready-original path (`claude/mattpocock` → `docs/agents`), so `docs/agents/mattpocock.md` is written when that flow is selected and never otherwise. Keying on the flow id is structural rather than coded.
  - **`setup-project` declares `disable-model-invocation: true`**, matching every other chain entry, so the generated `AGENTS.md` claim that the steps are user-invoked stays true for the first step too.
- Considered options:
  - **A flow-owned file, as FR-39 and the plan write it** — rejected. v0.12 and v0.13 each acquire a near-copy of an interview that is about the FastAPI template, not about the flow.
  - **One shared file declared in every flow's `paths`** — rejected. It renders identical bytes for every flow, so the hand-off paragraph cannot name the flow's own setup skill, which is the one part that had to vary. Declaring one `src` under three catalog entries also makes "which entry owns this path" unanswerable for `upgrade` and for the report.
  - **A `chain` field in `manifest.json`** — rejected. The manifest holds pins, ids, and paths; these are paragraphs of English prose, and prose in JSON is unreviewable in a diff. It would also not remove the table, because the hand-off paragraph stays prose either way.
  - **Deriving the chain from `disable-model-invocation: true`** — rejected, although the sets match exactly at the current pin: measured 2026-08-14, the six skills declaring it are precisely the chain entries, and the six that do not are precisely the tools a step reaches for. Frontmatter yields a set, and a chain needs an order.
- Consequences: adding a flow in v0.12 becomes a fixed checklist — a manifest entry, its vendored paths, one table entry, one `docs/agents/<flow-id>.md` — which is the property this decision exists to buy. `setup-project` becomes a managed path in the stamp inventory from v0.11, so a v0.10 project receives it as an added file on `upgrade`. Moving it into a flow's `paths` later would retire a managed path under the ADR-014 obsolete-file rules; that is the reversal cost, and it is accepted. The chain sentence is authored prose stating a fact about vendored content, so [ADR-023](adr-023-upstream-facts-drift-guard.md) requires it to be guarded: the same session decided an offline test asserting that the chain's skills still declare `disable-model-invocation: true`, which fails the pin bump rather than the user.
