## Problem Statement

Starting a production-grade FastAPI project that is ready for AI-assisted development requires assembling many pieces by hand: the base template, Canonical Content (`AGENTS.md` and `.agents/skills/`), optional Agent Target discovery files, MCP server setup, and design documentation. dev-ready is a CLI, run via `uvx dev-ready`, that scaffolds all of this in one command.

## Functional Requirements

FR-1. The user can run `uvx dev-ready` (or `uvx dev-ready init <project-name>`) to generate a new project in a target directory.

FR-2. Generation uses a two-stage approach:
- Stage 1: fetch the upstream base template (fastapi/full-stack-fastapi-template) at the exact commit pinned in `manifest.json`.
- Stage 2: apply the dev-ready overlay on top: Canonical Content, selected Agent Target Pointer Stubs and configuration, MCP server configuration, and design-doc templates.

FR-3. The CLI prompts interactively for project name, and which optional overlay components to include. A non-interactive mode (`--yes` with defaults, flags for each choice) must exist for CI and scripted use.

FR-4. All upstream content is fetched at a pinned commit recorded in `manifest.json`. The CLI never fetches "latest" at generation time.

FR-5. The generated project must work immediately: dependencies resolvable, containers buildable, health check endpoint reachable, without manual fixes.

FR-6. The CLI reports clearly what was generated and what the user should do next.

## Functional Requirements — v0.2

FR-7. Prune upstream repo-maintenance files. The generated project must not contain files that only make sense inside the upstream template's own repository. A `prune` list in `manifest.json` (separate from `exclude` — see ADR-006) removes them at generation time. Initial list, audited against a real v0.1.3 generation:

- `.github/workflows/` repo-maintenance workflows: `issue-manager.yml`, `labeler.yml`, `add-to-project.yml`, `latest-changes.yml`, `smokeshow.yml`, `detect-conflicts.yml`, `zizmor.yml`, `guard-dependencies.yml`, and the `.github/labeler.yml` config. KEEP the workflows that test the user's own app: `test-backend.yml`, `test-docker-compose.yml`, `playwright.yml`, `pre-commit.yml`, plus `dependabot.yml`. (Amended 2026-08-04: `deploy-production.yml` and `deploy-staging.yml` were listed here from v0.2 on the stated grounds that they "reference upstream's own servers and secrets". Reading them at the pinned commit contradicts that — `deploy-production.yml` opens with `# Do not deploy in the main repository, only in user projects` and the guard `if: github.repository_owner != 'fastapi'`. Upstream wrote both **for downstream users**, and `deployment.md` — which dev-ready keeps — spends its Continuous Deployment sections teaching how to use them. Pruning them removed a working deployment path and made the retained documentation describe files that were no longer there. Both leave the prune list under FR-38. Accepted consequence: a user who publishes a release before setting up a self-hosted runner gets a deployment job that waits for a runner label that does not exist yet; that is upstream's own behaviour for its intended audience, and `deployment.md` is where it is explained.)
- `CONTRIBUTING.md` (contributing to the template, not to the user's project)
- `release-notes.md` (upstream's release history)
- `img/` (upstream README screenshots and GitHub social-preview images, ~7 files)
- `scripts/add_latest_release_date.py` (upstream release tooling; other scripts stay)
- `hooks/post_gen_project.py` (dead file: cookiecutter-era hook, not referenced by the template's `copier.yml` — its `_tasks` only runs `.copier/update_dotenv.py`)
- `README.md` (upstream's template README; replaced per FR-8)

KEEP even though they look upstream-ish: `development.md`, `deployment.md` (genuinely useful to the user), `.pre-commit-config.yaml`, root `package.json`/`bun.lock` (bun workspace wiring), `.gitattributes`, `.agents/` and `.claude/` skill content not already excluded. (Amended 2026-07-17: `.copier/` and `.copier-answers.yml` were originally kept to enable `copier update`, but are now pruned by `generate` (`e096aaf`) — Copier metadata does not belong in an end-user project. The upgrade path is `dev-ready upgrade` (FR-22), not `copier update`. See the ADR-005 amendment.)

FR-8. Project README. Because FR-7 prunes the upstream `README.md`, the overlay writes a project-specific `README.md` (templated with the project name, brief stack summary, and the same commands as canonical `AGENTS.md`). The overlay's no-overwrite rule is preserved: prune removes the upstream file first, so there is no collision.

FR-9. Leak guard in verify. `verify_project` gains a forbidden-paths check (at minimum `.git`, `copier.yml`, `copier.yaml`) so a future upstream or Copier behavior change that reintroduces the v0.1.3 `.git`/`copier.yml` leak fails generation loudly — in CI at bump time, before it ever reaches users.

FR-10. Handoff Protocol overlay (optional component, alongside skills/mcp/docs). Generated projects could include a multi-agent handoff scaffold: a `docs/handoffs/` directory with role and handoff templates (tech lead -> senior engineer -> junior engineer -> QA/Security/SRE, see ADR-007), and an agent-roles section in canonical `AGENTS.md`. It was selected like the other components (`--no-handoff`; the original `--no-agents` name was the deprecated alias described by FR-26). **Retired as product surface in v0.9 by FR-35 ([ADR-020](decisions/adr-020-handoff-protocol-not-generated.md))** — v0.9 stops generating the scaffold. That product decision did not change this repository's process; [ADR-021](decisions/adr-021-internal-process-v3-spec-loop-only.md) retired the internal Handoff Protocol separately four days later.

- FR-37 (v0.10, shipped). Tech stack and standards sources in the generated `AGENTS.md`. The vendored `code-review` skill resolves its Standards axis by looking for "anything in the repo that documents how code should be written, such as `CODING_STANDARDS.md` or `CONTRIBUTING.md`" — and dev-ready prunes upstream's `CONTRIBUTING.md`, so a generated project offers that axis nothing and it falls back to the built-in smell baseline. No template mentions the test runner, linter, or type checker by name; `AGENTS.md` says only `bash scripts/test.sh`. The generated `AGENTS.md` therefore names the tools an agent needs to implement and verify a change, and states that it is itself the project's standards source. It belongs there rather than in a skill or a separate file: the stack applies at every step, `AGENTS.md` is the one file every session loads, and a fixed base template (ADR-001, ADR-002) makes the stack a constant rather than a per-project variable until FR-27 adds a second template.
- FR-38 (v0.10, shipped). Secret hygiene and credential disclosure in generated projects. Four defects found by generating a project with the released v0.9.0 and reading what it produced; all four are shipped-product defects rather than new capability, which is why they land in v0.10 rather than waiting for v0.11.
  - **(a) `.env` is not ignored by git, and dev-ready is the one that put secrets in it.** None of the three generated `.gitignore` files — root, `backend/`, `frontend/` — carries an `.env` pattern, while `_template_data` in `src/dev_ready/generate.py` writes a per-project random `SECRET_KEY`, `POSTGRES_PASSWORD` and `FIRST_SUPERUSER_PASSWORD` into it. A user's first `git add .` therefore commits their own secrets into history. The root `.gitignore` joins the FR-7 prune list and the overlay writes a replacement — the same prune-and-replace shape FR-7 and FR-8 already use for `README.md`, so no new mechanism is introduced and `check`, `upgrade`, and the ADR-014 rules apply unchanged. The replacement carries upstream's existing entries plus `.env` and `.env*`. dev-ready owning the file means upstream additions no longer arrive automatically, so a dedicated maintainer check (`scripts/check_ignore_drift.py`) resolves the pin, reads upstream's root ignore file **at the pinned commit itself**, and fails the weekly bump when it diverges from the adopted copy. (Corrected 2026-08-05: this clause previously said the weekly CI's regenerated project is where the divergence is detected. It is not, and cannot be — pruning is applied as a Copier exclude at *fetch* time, so upstream's file never reaches a generated project and nothing downstream of generation can compare against it. The check has to reach the commit, which is why it is the one piece of FR-38 that makes a network call.) Upgrade reach is narrower than it looks: a project generated before this change already carries upstream's own unmanaged copy at that path, which ADR-014 forbids replacing, so it is reported as a conflict and then skipped rather than receiving the file — see the FR-38 spec's Implementation Decisions for why no special case was added.
  - **(b) Nothing tells the user their login exists.** Neither the generation report's next steps nor the generated `README.md` names `FIRST_SUPERUSER` or says where its password is, so a user who runs `docker compose watch` reaches a login screen with no way to pass it. Both gain it, along with the ordering fact that makes it urgent: `init_db` in the generated backend selects the user by email and creates one only when absent, so changing `FIRST_SUPERUSER_PASSWORD` after the first start is **silently ineffective** — the file changes, the login does not, and no error is raised.
  - **(c) `BACKEND_CORS_ORIGINS` ships a third party's domain.** Every generated `.env` allows `http://localhost.tiangolo.com`, upstream's own local-testing hostname. It is removed from the generated value. `.env` is configuration, so this is permitted by ADR-022.
  - **(d) The FR-7 prune list is corrected**: `deploy-production.yml` and `deploy-staging.yml` are restored, per the 2026-08-04 amendment recorded at FR-7.
  - Accepted residue, recorded rather than fixed: `deployment.md` keeps roughly seven stale lines under `## GitHub Actions Environment Variables` describing `LATEST_CHANGES` and `SMOKESHOW_AUTH_KEY`, whose workflows are correctly pruned. Repairing them means pruning and rewriting all 352 lines of a document that is otherwise accurate and genuinely useful, which is not worth it.
- FR-39 (v0.11, planned). `setup-project` — an always-generated setup step at the head of the development loop. The generated loop chain currently starts at `grill-with-docs` and never names the vendored `setup-matt-pocock-skills`, so nothing tells an agent that a run-once configuration step exists. A dev-ready-original skill `setup-project` becomes the loop's first chain entry and its single setup entry point: it interviews the user for the two `.env` values that are genuinely per-project — the superuser email, and the superuser password with "keep the generated random value" as the default — behind them one gate for SMTP and Sentry defaulting to no, and then delegates to `setup-matt-pocock-skills` for the issue tracker, triage labels, and domain-document layout. `SECRET_KEY` and `POSTGRES_PASSWORD` are displayed and never asked for; asking a user to invent them lowers security. `DOMAIN`, `FRONTEND_HOST`, `BACKEND_CORS_ORIGINS`, `ENVIRONMENT`, and `DOCKER_IMAGE_*` are never asked for: at setup time the correct value of `DOMAIN` is `localhost`, and writing anything else breaks the project on day one, because `DOMAIN` is interpolated into Traefik `Host()` router rules and into `VITE_API_URL`, a build argument baked into the frontend bundle. The skill closes by pointing at `deployment.md` for the deployment-time values. It must detect a project that has already been started and say plainly that applying the change requires `docker compose down -v` and that this destroys existing data, then stop and let the user decide — it never runs that command. `setup-matt-pocock-skills` is vendored under the FR-16 byte-equality drift guard and is neither forked nor edited; the cross-reference is prose in dev-ready's own file, covered by a test asserting the referenced identifier is still one of the loop's steps. The skill is delivered as a dev-ready-original path inside the development loop's `paths`, exactly as `claude/spec-loop` → `docs/agents` already is, so it is not added to the vendored path list and the drift guard is untouched.
- FR-40 (v0.11, planned). The full `awesome-design-md` set as Design References. Two of the pinned repository's 103 design documents are vendored today, which is arbitrary curation of content whose whole value is choosing a visual direction. All of them are vendored, as ordinary catalog items in the `design` Category. Delivery is by vendoring into the wheel rather than by fetching at generation time: markdown compresses to about 30%, so 103 documents cost roughly 766 KB in the wheel, and every existing mechanism — the FR-16 drift guard, the stamp inventory, `upgrade`, ADR-014, and the THIRD_PARTY_NOTICES entry, which needs only additional `paths` under the same repository and pin — keeps working with no changes. Generation-time fetching was rejected: ADR-002 forbids resolving anything but the pinned commit, so it would deliver identical bytes while requiring a fourth integration mode beyond ADR-008's, and an overlay file absent from `build_overlay_content` is classified as obsolete by the ADR-014 rules, so an untouched design document would be **deleted** on the next `upgrade`. The entries are produced by a maintainer derivation script, not typed by hand, per ADR-019's standard; the source is a directory listing rather than a TypeScript literal, so the script is considerably simpler than FR-33's. Selection stays **multi-select**: `design-stripe` and `design-linear` are already multi-select and are recorded together in existing v5 stamps, so single-select would break the `--design` contract and make those projects un-upgradeable, to prevent a cost a user can only incur deliberately — and a project legitimately wants different directions for different surfaces. dev-ready records no mapping from a Design Reference to the surface it applies to; where more than one is selected, that mapping is the user's to write in their own `docs/architecture.md`, and no such mechanism is to be invented.
- FR-41 (v0.11, planned). MIT notice propagation into generated projects. The two Apache-2.0 skills carry their `LICENSE.txt` into every generated project, while the twelve MIT `mattpocock/skills` development-loop skills carry no copyright or permission notice at all — and MIT's terms require the notice to travel with copies. The gap has existed since v0.7 and FR-32 did not create it, but v0.10 is the first version whose own `THIRD_PARTY_NOTICES.md` states that copies written into a generated project may be modified and are therefore derived works, and whose generation injects dev-ready's own text into those files (FR-32). The repair is the mechanism already in use for the Apache skills: the upstream notice is vendored under the existing pin and written alongside the loop skills, which makes it a new managed path, a stamp-inventory entry, and one more line of FR-16 drift-guard coverage. That is why it is not a release-day edit and why it did not land in v0.10 — the release phase carries no feature work. Recorded as an observation on 2026-08-03 and scheduled by the 2026-08-09 amendment in [version-plan.md](version-plan.md); no legal conclusion is drawn there or in any user-facing document.

- FR-42 (v0.11, planned). Engineering Flow selection and the interactive rework ([ADR-024](decisions/adr-024-engineering-flow-selection-spine.md), amending [ADR-017](decisions/adr-017-category-first-selection.md) and [ADR-012](decisions/adr-012-spec-loop-bundle-and-methodology-layering.md)). The development loop becomes the **Engineering Flow**, asked first and named for its source. Three of the five parts are defects in what v0.9 shipped, of the kind FR-36 corrected in v0.10, found by reading the shipped v0.10.1 selection path rather than its design: the loop prompt returns early whenever the catalog declares one loop (`collect.py:258`), so it has **never been asked**; both branches of `Use the Default Set?` resolve to byte-identical selections, because `default_set.enhancements` is empty and one loop exists, so the flow's first question **changes nothing**; and `dev` is listed among the Category checkboxes and then force-added regardless (`collect.py:186-197`), an option whose selection has no effect, in a Category whose only member is the loop. The rework: the Flow question is asked even at one option, because its job there is disclosure rather than choice; the item id `spec-loop` is renamed `mattpocock` with `superpowers` and `addyosmani` reserved, since all three candidate flows are spec-driven and the old id therefore cannot say *which*, and `upgrade` carries a permanent `spec-loop` → `mattpocock` alias while the stamp stays at version 5 (no field is added, removed, or re-typed); Catalog Items gain a `title` for display and a `status` marking a flow announced but not yet shipped, which is **listed in the interactive menu and rejected by the flags** with an error naming it as unavailable rather than unknown; `dev` leaves the presented Category set while remaining a Category id everywhere it is recorded; the four optional Categories are walked one at a time with no preceding filter, since declining a Category is pressing Enter on it and a filter reproduces one level up the failure FR-36 fixed; and the Default Set becomes a non-interactive concept, exactly what `--yes` resolves to. Placeholder entries say only `(coming soon)` — a version number in shipped UI lies as soon as the roadmap moves. The cost of `status` is accepted deliberately: it is a third catalog state that prompts, every selection flag, and the Generation Skill's trigger list must each handle, for an entry nobody can choose.
- FR-43 (v0.11, planned). Flow Chain guidance corrected, and a per-flow document. The generated loop guidance is one sentence (`overlay/rendering.py:26`) and it contradicts the skills it ships alongside, twice. It calls the loop "one end-to-end method" and prints an unconditional seven-step chain, while every vendored step declares `disable-model-invocation: true` — the model cannot invoke them at all, so **skipping is already the mechanism's default** and nothing enforces a chain. And it lists `tdd` and `code-review` as peers of `implement`, when the vendored `implement` calls both itself ("Use /tdd where possible"; "Once done, use /code-review"), which turns tools into phases. Like FR-36(e), this is generated documentation misdescribing generated content. The corrected chain is five entries — `grill-with-docs` → `to-spec` → `to-tickets` → `implement` → `improve-codebase-architecture` — with `tdd`, `code-review`, `diagnosing-bugs`, `codebase-design`, and `domain-modeling` named as what a step reaches for rather than what follows it. (This repository's own `AGENTS.md` describes four steps for itself and files `improve-codebase-architecture` under architecture hygiene; the product's fifth entry is a deliberate difference, not drift.) Three audiences get three documents: the generated `AGENTS.md` stays short and agent-facing — the correct chain, that steps are user-invoked, and one concrete skip criterion, since vague judgement guidance in an agent-loaded file is ignored; a new `docs/agents/<flow-id>.md`, written only when that flow is selected, carries the human-facing explanation, including that a flow need not complete in one session; and dev-ready's own `README.md` gains a short section for readers deciding whether to adopt it. The per-flow document is the structure FR-47 and FR-48 extend, one explainer per flow. Sequencing: FR-43 must ship with FR-39, which puts `setup-project` at the head of this very chain — separating them writes the same sentence twice.
- FR-44 (v0.11, planned). CLI presentation ([ADR-003](decisions/adr-003-distribution-via-uvx.md), 2026-08-12 amendment). The interactive screens and the generation report are visually plain next to the installers users meet elsewhere. This was raised as an argument for npx distribution and is separated from it: what reads as polished in `npx skills add` is `@clack/prompts` — framed boxes, grouped headings, colour — not the launcher. The work is questionary styling plus report layout, reachable from Python with no new runtime and no change to distribution. It ships with FR-42 because it rewrites the same screens; done separately, the prompt surface is edited twice.
- FR-45 (v0.11, planned). Plugin manifests for Claude Code and Codex. The Generation Skill is installable today through the cross-agent installer (`npx skills add MoofonLi/dev-ready --skill dev-ready`), which reaches Claude, Codex, and ~70 other agents and publishes nothing to npm — the repository itself is the source. What it lacks is a **browsable storefront**, and discovery is now the binding constraint on v1.0: the 2026-08-09 amendment left the real-users gate deciding on Branch A alone, so attributable external users are the only currency. Both ecosystems accept a thin manifest over an existing directory — Claude at `.claude-plugin/plugin.json`, Codex at `.codex-plugin/plugin.json` with `name`, `version`, `description`, and a `skills` path — and Codex discovers skills by the `skills/<name>/SKILL.md` layout this repository already uses, so both manifests point at the unchanged `skills/dev-ready/` and duplicate no content. The cross-agent installer remains the documented primary channel; removing it would strand every agent without a storefront. These manifests are transcribed from moving external specifications with no FR-16-style guard, so both must be re-verified at bump time — the same standing exposure ADR-015 recorded for agent paths before FR-33 closed it.
- FR-46 (v0.12, planned). Skill Delivery Mode ([ADR-025](decisions/adr-025-skill-delivery-mode.md), partly superseding [ADR-015](decisions/adr-015-agent-targets-canonical-content-pointer-stubs.md)). Pointer Stubs are retired in favour of a recorded user choice between `symlink` and `copy`, matching the convention the reference installer defines (`add.ts:770-800`: `InstallMode = 'symlink' | 'copy'`, prompted as *Symlink (Recommended)* against *Copy to all agents*). ADR-015 rejected symlinks twice on three mechanics; one is now measurably wrong — a Windows **junction** needs no elevation, and the reference installer creates exactly that (`installer.ts:255-256`). The mode is asked when at least one selected Agent Target declares a directory other than `.agents/skills/`; because dev-ready always writes Canonical Content, one non-standard target already gives a link a real destination, which is where this rule departs from the reference installer's. `--skill-delivery symlink|copy` defaults to `copy`, the mode that survives `git clone` on every platform. There is **no platform-conditional fallback**: a `symlink` selection that cannot be honoured fails with a message naming the cause, because a detected fallback would make one dev-ready version produce different output on different machines (NFR-1) while an explicit selection is an input. Symlinks are **not** inventoried in the stamp — a link is derived state, and leaving it out is also what keeps `upgrade`'s path-traversal guard (`upgrade.py:33-42`) intact, since that guard refuses any path traversing a symlink and would otherwise refuse dev-ready's own managed files; copies are inventoried by content hash as today. Existing stubs retire through the ADR-014 obsolete-file rules with user edits preserved. `CLAUDE.md` keeps `@AGENTS.md` and is out of scope: that is Claude Code's native import, not a dev-ready indirection. Two costs are permanent and belong in the generation report: a `symlink`-mode project's agent directories are machine-local (a junction has no git representation at all), and junction targets are absolute, so moving the project breaks them until `upgrade` re-runs. This FR takes a version to itself for the reason FR-26 did — it touches the write path, the stamp inventory, `verify`, `upgrade`, and a migration.
- FR-47 (v0.12, planned). Second Engineering Flow — `obra/superpowers` (MIT, verified 2026-08-12) — and flow recommendation inside the Generation Skill. The recommendation cannot precede the second flow: with one flow there is nothing to recommend between. It lands **inside FR-34's interview** rather than as a new skill, because that interview already questions the user and maps answers onto a selection, and `--development-loop` is a flag it already composes; a second interviewing skill would also violate FR-34's own rule that the interview must not compose a command asking a second set of selection questions. The recommendation is written as **selection criteria** — "you need <observable need> → this flow" — and never as a comparison of the three upstream projects. dev-ready's vendored content is held to upstream by FR-16's byte-equality guard; a comparative claim about a project dev-ready does not ship has no such guard and silently becomes false when that project changes. Criteria describe the user's need, which is stable; comparisons describe upstream's features, which are not.
- FR-48 (v0.13, planned). Third Engineering Flow — `addyosmani/agent-skills` (MIT, verified 2026-08-12). Adds the third flow and its per-flow document, and removes the last `status` placeholder from the menu.
- FR-49 (v0.13, planned). Token Optimize additions, each gated independently. `ayghri/i-have-adhd` (MIT, verified 2026-08-12) is text and vendors under ADR-008's vendor mode. `headroomlabs-ai/headroom` (Apache-2.0, verified 2026-08-12) is **not a skill** — it is a library, proxy, and MCP server published to PyPI as `headroom-ai` — so it is a pinned-dependency `mcp` item alongside `code-memory`, and no NOTICE propagation is triggered because nothing is redistributed. headroom carries the risk profile that disqualified Graphify and must clear it before it is scheduled: its documented flow wraps the agent session, starts a local proxy, and installs Serena, and its Codex instructions require pointing a client at an **absolute binary path**, which dev-ready cannot write without binding the project to one machine (NFR-1, NFR-5). It is admissible only if a lean extra launches cleanly as `uvx headroom-ai[...]==<pin> mcp serve` with no API key, no writes outside the project, and standalone value from MCP mode alone; otherwise it stays a recorded candidate, as Graphify is. Both items join the Token Optimize Category, whose description widens to cover output legibility as well as token spend: `i-have-adhd` keeps an agent's answer findable while `caveman` makes it shorter and cheaper, so neither substitutes for the other, and `caveman` has always straddled both halves. The Category id is unchanged — descriptions enter neither the flag contract nor the stamp.

## Non-functional Requirements

NFR-1. Reproducibility: two runs of the same dev-ready version produce identical output (modulo user inputs).

NFR-2. Maintainability: designed for a solo maintainer. Upstream tracking is automated (weekly CI bump PR); no fork of upstream is maintained.

NFR-3. Distribution: installable and runnable via `uvx` with zero prior setup beyond uv itself. Python >= 3.12.

NFR-4. Offline behavior: fail fast with a clear message when the network is unavailable; never generate a partial project.

NFR-5. Cross-platform: macOS, Linux, Windows.
